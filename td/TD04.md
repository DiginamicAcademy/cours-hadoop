## Introduction — un fichier qui bouge, un traçage qui reste

Jusqu'ici, les données bougent quand **vous** lancez une commande (`cp`, `hdfs dfs -put`). NiFi change la donne : **vous** posez le flux, les **fichiers bougent tout seuls**. Et surtout : **chaque déplacement est enregistré** — l'heure, le nom, le chemin, le processeur qui l'a traité. C'est ce qui se passe *entre* l'ingestion et le stockage, et c'est invisible en shell : NiFi le rend visible.

> ⚠️ **Premier contact.** Le cours (séquence 07) expliquera les FlowFiles, les controller services et la back pressure. Ce TD se contente de faire **apparaître** le principe en 20 minutes : un fichier traverse un processeur, un historique apparaît.

## Tempo A — guidé : un seul processeur, une seule preuve

> Ouvrez NiFi : `https://localhost:8443/nifi` (certificat auto-signé, puis login : `etudiant` / `etudiant` ou le couple remis par le formateur).

**1. Créez un petit fichier d'entrée.** Sur la machine hôte, dans le dossier monté `nifi/input/` (c'est `/opt/nifi/input` vu du conteneur) :

```bash
echo "track,year,streams
Chanson A,2023,100
Chanson B,1975,200" > nifi/input/test.csv
```

**2. Glissez un processeur `GetFile`** au centre du canvas et configurez-le :

| Propriété | Valeur |
|---|---|
| `Input Directory` | `/opt/nifi/input` |
| `File Filter` | `.*\.csv` |
| `Keep Source File` | `false` |

**Settings** : cochez `auto-terminate` sur **success** (pas de successeur, le processeur doit savoir s'arrêter).

**Démarrez** le processeur (▶). Le compteur **out** passe à `1` — un FlowFile a été créé. Vérifiez : `test.csv` a **disparu** du répertoire d'entrée.

**3. Ouvrez Data Provenance** (menu global, icône horloge). L'événement `RECEIVE` apparaît avec l'heure, le processeur, la taille. Cliquez dessus → onglet **Content** : vous pouvez **télécharger** le contenu du FlowFile pour vérifier qu'il est intact. L'onglet **Lineage** montre le graphe : `GetFile` seul, un nœud.

C'est la donnée qui raconte son histoire : **où elle est passée et à quelle seconde** — sans écrire un seul log.

**4. Ajoutez un processeur `PutFile`** et câblez :

```
GetFile  [success] →  PutFile
```

Propriétés de PutFile :

| Propriété | Valeur |
|---|---|
| `Directory` | `/opt/nifi/output` |
| `Conflict Resolution Strategy` | `replace` |

Settings de PutFile : cochez `auto-terminate` sur **success** et **failure**.

Déposez un deuxième fichier `test2.csv` (même format). Le compteur de PutFile passe à `1`. Vérifiez sur le master :

```bash
ls nifi/output/   # test2.csv est là
```

**Data Provenance** affiche maintenant **deux** événements : `RECEIVE` sur GetFile, `CONTENT_MODIFIED` sur PutFile (ou `SEND` — le nom dépend de NiFi). Le graphe de **Lineage** montre deux nœuds reliés : le fichier est passé de GetFile à PutFile. La traînée est complète.

## Tempo B — entraînement libre

> **Consignes** : en solo ou en binôme, sans support. Vérifiez en relançant les commandes.

**Q1.** Le fichier arrive dans `/opt/nifi/output` avec son **nom d'origine** (`.csv`), alors que le contenu reste du CSV brut. Pourquoi NiFi ne renomme-t-il pas en `.tsv`, et quel outil se fierait-il au nom ?

**Q2.** Remettez `Conflict Resolution Strategy` de PutFile à **`fail`** (la valeur par défaut), puis déposez **deux fois** le même `test.csv`. Que devient le FlowFile du deuxième dépôt ? Où le trouvez-vous dans Data Provenance ?

**Q3.** Vous déposez un fichier `.csv` contenant **une seule ligne de texte quelconque** (pas de colonnes, pas de header). GetFile le traite-t-il ? PutFile le traite-t-il ? Où se trouve la preuve ?

## Pour aller plus loin — de un à trois processeurs

- **Filtrer par taille** : ajoutez une propriété `Minimum File Size = 100 KB` sur GetFile. Un petit fichier de test (quelques octets) ne traverse plus. C'est le premier filtre de données.
- **Un processeur qui transforme** : insérez `ConvertRecord` entre GetFile et PutFile, avec un `CSVReader` (séparateur `,`, quotes `"`, `Treat First Line as Header = true`) et un `CSVRecordSetWriter` (séparateur `\t`). Le fichier arrivant en sortie est maintenant du **TSV** — la même conversion que le script `../annexes/utils/7-prepare-spotify-tsv.py`, mais en flux continu. (Le nom reste `.csv` : c'est l'annexe de l'EX 07 qui le corrige via `UpdateAttribute`.)
- **Le fil rouge** : ce flux à 3 processeurs est exactement l'amorce de l'[`EX 07 — NiFi`](../exercices/07-nifi.md) — qui le prolonge vers HDFS (`PutHDFS` ou `hdfs dfs -moveFromLocal`) et ajoute la gestion des échecs (`failure` câblée).

**À conserver dans le rapport** : la capture Data Provenance (Lineage) du step 4, et une phrase sur la différence entre « le fichier est arrivé » (le `ls` du master) et « le fichier a été *traité par* GetFile puis *écrit par* PutFile à telle seconde » (Data Provenance).
