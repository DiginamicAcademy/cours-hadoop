## Tempo A — la table, les `put`, le `scan`

### Step 1-2 — le shell et la table

`hbase shell` → prompt `hbase:001:0>`. `create 'chrono', 'stats'` répond `0 row(s)` — la création d'une table **aussi** ne confirme rien par l'affirmative : HBase répond peu, c'est une constante du shell.

### Step 3 — les trois `put`

Chaque `put` répond `0 row(s) in 0.… seconds`, dans l'ordre : `2023`, `1975`, `2021`. Aucune mention du nombre de cellules écrites — lire la réponse comme un `OK` silencieux.

### Step 4 — le `scan` trié

```
ROW     COLUMN+CELL
1975    column=stats:total, timestamp=..., value=4206105352
2021    column=stats:total, timestamp=..., value=73808103039
2023    column=stats:total, timestamp=..., value=25808484104
3 row(s)
```

Les trois lignes sont là (les `put` ont donc écrit), mais **triées par rowkey** : `1975`, `2021`, `2023` — pas dans l'ordre d'insertion (`2023` d'abord). L'ordre d'arrivée n'a **aucun** pouvoir sur le rang de lecture.

### Step 5 — le `get`

`get 'chrono', '1975'` rend uniquement la ligne `1975` et sa colonne — la lecture **directe par clé**, sans scanner tout le reste.

## Tempo B — réponses

**Q1.** La **rowkey** est triée **lexicographiquement** (ordre des octets de la chaîne), indépendamment de l'ordre d'insertion. `'1975'` et `'2021'` commencent par `'1'` (0x31) < `'2'` (0x32) de `'2023'` → `1975` et `2021` passent avant `2023`, quel que soit l'ordre des `put`. Ce n'est pas la valeur numérique qui décide, c'est la chaîne d'octets (et c'est pourquoi des clés à longueur variable casseraient le tri, comme au shuffle).

**Q2.** Oui, les `put` ont écrit (le `scan` le montre). Mais la réponse `0 row(s)` **ne prouve rien** — HBase ne « confirme » pas. Les seules preuves : un **`scan`** (tout lire) ou un **`get` par rowkey** (lire la ligne). C'est exactement la réponse que donnera l'EX 06 à « le `put` d'HappyBase ne confirme rien » : la donnée se vérifie par la lecture, pas par l'écriture.

**Q3.** Le tri du **shuffle/sort MapReduce** (TD01 : c'est le `sort` du pipe qui a rendu possible le reducer) — la même règle d'octets sert aux rowkeys et à l'ordre des clés avant le reduce. Hive (TD02) affiche les années croissantes parce que ses clés `released_year` sont ordonnées au shuffle puis triées par le requête ; HBase les sert triées parce qu'elles **sont stockées** triées. Même règle commune : l'ordre lexicographique des clés.

## Tempo C — HappyBase

Le ThriftServer est lancé (`./start-thrift.sh`), `jps | grep Thrift` confirme.

**Étape 3 — connexion** :

```python
import happybase
connection = happybase.Connection('127.0.0.1', 9090)
table = connection.table('chrono')
```

Pas de `connection.open()` — HappyBase se connecte automatiquement à la création.

**Étape 4 — les trois `put`** :

```python
table.put('2023', {'stats:total': '25808484104'})
table.put('1975', {'stats:total': '4206105352'})
table.put('2021', {'stats:total': '73808103039'})
```

Même comportement que le shell : pas de confirmation, la seule preuve est la lecture.

**Étape 5 — le `scan`** :

```python
for key, data in table.scan():
    print(key, data)
```

Sortie attendue :

```
b'1975' {b'stats:total': b'4206105352'}
b'2021' {b'stats:total': b'73808103039'}
b'2023' {b'stats:total': b'25808484104'}
```

Même ordre trié que le shell (`1975`, `2021`, `2023`).

**Étape 6 — le `get`** :

```python
print(table.row('1975'))
```

Sortie attendue :

```
{b'stats:total': b'4206105352'}
```

Même résultat que `get 'chrono', '1975'` dans le shell.

**Étape 7 — fermeture** :

```python
connection.close()
```

## Pour aller plus loin

- **Intervalle `1975→2021`** : le `scan` avec `STARTROW`/`STOPROW` rend les clés du bloc demandé (ici `1975`, `2021` ; `2023` est hors de `[1975, 2021)`). L'ordre est dans la clé : on lit une **plage**, pas tout le stock.
- **Versionnage** : refaire `put 'chrono', '2021', 'stats:total', '…'` ne « corrige » pas la cellule : le `timestamp` change et l'ancienne version reste en table (HBase versionne). Rien n'est écrasé au sens d'une mise à jour classique — la lecture prend la dernière version.
- **Les 50 années** : les 50 rowkeys du TD02 (1930→2023) sont servies triées par le `scan`, comme Hive les regroupait — mais avec « donne-moi cette rowkey » en **lecture directe**, là où Hive devait tout lire.
